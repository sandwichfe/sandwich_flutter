# embyx 分片影片关联方案

解决「一部影片被切成 `_1` / `_2` 多个文件，扫描后变成两条互不相关的记录」的问题。

本文只做设计，不含代码改动。

## 目标与非目标

**目标**

- 扫描主流程保持不变：每个物理文件仍然是一条 `items` 记录，`UpsertItem` 不动。
- 新增一张归属表，把同属一部影片的分片串起来。
- 影片详情页能看到同组的其他部分（一个列表）。

**非目标（本阶段明确不做）**

- 不做多版本（同片不同分辨率/编码的选择器）。
- 不做跨段连续播放（播完第 1 段不自动切第 2 段）。
- 不做总时长聚合、不做版本选择器、不做物理文件合并。
- 不改 `items` 表结构。

> 多版本方案见 `MULTI_VERSION_PLAN.md`，当前方向已暂缓。

## 现状

| 事实 | 位置 |
|---|---|
| 一个文件一条 `items` 记录，`Type` 硬编码 `"Movie"` | `internal/media/scan.go:536-564` |
| 标题解析只出标题 + 年份，不识别分片序号 | `internal/media/scan.go:650-669` |
| `cleanTitle` 把 `_` 换成空格，`3070118_1` → `3070118 1` | `internal/media/scan.go:671-676` |
| `purgeMissingItems` 按 `items.path` 判断存活 | `internal/media/scan.go:341-410` |
| 已有逐级迁移机制，`schemaVersion = 8` | `internal/store/store.go:37-99` |
| 已有 `/Items/{itemId}/Similar` 可作为新接口的实现参照 | `internal/httpapi/` |

## 总体思路

```
扫描（完全不变）
  └─ 探测 → 构造 Item → UpsertItem
        └─ 追加一步：从 path 推导 group_key → 写 item_groups（失败不影响主流程）

详情页
  └─ GET /Items/{itemId}            → 拿到 PartIndex / PartCount，先画徽标
  └─ GET /Items/{itemId}/Siblings   → 拿到兄弟列表，渲染「本片共 N 部分」
```

关键取舍：**关联信息是扫描的旁路产物，不是主流程的一环**。写归属失败只记日志，不能让文件入库失败。

## 数据模型

### 单归属，不是多对多

一个物理文件只可能是一部作品的一个片段，所以用**归属表**（`item_id` 是主键）而不是成对的关系表：一行都不用写两遍，也不会有 N² 冗余。

```sql
CREATE TABLE IF NOT EXISTS item_groups (
    item_id    TEXT PRIMARY KEY,           -- 一个 item 只属于一个组
    group_key  TEXT NOT NULL,              -- 组标识，算法见下节
    part_index INTEGER NOT NULL DEFAULT 0, -- 从文件名解析的原始序号（1 起）
    part_count INTEGER NOT NULL DEFAULT 0, -- 组内实际成员数（冗余，省一次 COUNT）
    relation   TEXT NOT NULL DEFAULT 'part'
);

CREATE INDEX IF NOT EXISTS idx_item_groups_key ON item_groups(group_key);
```

字段说明：

| 字段 | 作用 | 备注 |
|---|---|---|
| `item_id` | 主键 | 天然表达「单归属」，重复写入用 `ON CONFLICT(item_id) DO UPDATE` |
| `group_key` | 分组依据 | 只有分片文件才写行，普通影片不写 |
| `part_index` | 排序用 | 存原始序号，不存组内位置；缺号时才看得出原始编号 |
| `part_count` | 显示用 | 冗余，避免详情页每次 `COUNT(*)` |
| `relation` | 预留 | 固定 `part`，将来可扩展 `series` / `collection` |

### 为什么不像多版本那样建子表

多版本需要「一个作品多个可播放源」，必须把文件从 `items` 里拆出去。分片不需要——每个片段本身就是一个完整可播条目，用户点哪段播哪段，进度各自独立。所以只需要一层**指向关系**，`items` 一行不用动。

## group_key 算法

这是整个方案唯一有风险的地方，也是唯一的自动关联依据。

```
groupKey(libraryID, root, path):
    base    := 去掉扩展名的文件名              // "3070118_1"
    parsed  := parsePartSuffix(base)          // {stem:"3070118", index:1}
    if parsed == nil { return "" }            // 不是分片，不参与分组
    relDir  := path 相对库根 root 的目录部分
    return libraryID + "|" + lower(replace(relDir, "\", "/")) + "|" + normalize(parsed.stem)
```

`normalize` = 小写 + 分隔符统一为空格 + 去两端装饰字符（复用 `cleanTitle` 的语义）。

### 能识别 / 不识别

| 能识别（带明确序号） | 不识别（一律不分组） |
|---|---|
| `_1` `_2` | `2160p` `1080p` `x265` |
| `-cd1` `-cd2` | 任意无序号后缀 |
| `part1` `part2` / `pt1` `pt2` | 纯标题差异 |
| `disc1` `disc2` / `dvd1` `dvd2` | |
| `上` `下` / `前篇` `后篇` | |
| `(1)` `(2)` / `[1]` `[2]` | |

### 三条铁律

1. **必须带序号**。没有序号就不分组，宁可漏关联，也不误关联。
2. **必带 `library_id` 和相对目录**。否则两个库里同名的 `3070118_1` 会串成一组；同一库里两个不同目录的同名文件同理。
3. **只做字符串级归一化**，不做「标题 + 年份」的模糊匹配。那是另一个量级的误判风险。

带相对目录的好处：整个库换盘符、换挂载点都不影响分组（与 `deriveItemID` 现有的路径派生思路一致）。

## 写入与一致性

### 三个写入时机

| 时机 | 动作 |
|---|---|
| 文件入库后 | `INSERT ... ON CONFLICT(item_id) DO UPDATE`，随后把同组所有成员的 `part_count` 刷新为当前成员数 |
| `purgeMissingItems` 删除 item | 显式删除对应归属行。**库内没有外键，必须手动删**，否则留下永久孤儿行 |
| 老库升级（8 → 9） | Go 侧回填：遍历 `items`，算 `group_key` 写入。不重扫也能补齐 |

### 增量跳过分支也要写一次

扫描有「指纹命中就跳过、不写库」的分支（`internal/media/scan.go:519-528`）。如果只在写入分支写归属行，那么归属行一旦缺失（老库未回填、手动删过），重新扫描也修不回来。

所以在跳过分支要补一次极轻量的 `INSERT OR IGNORE`。一行 SQL，不碰 `items`，不影响现有性能特征。

### `part_count` 的刷新

```sql
UPDATE item_groups
SET part_count = (SELECT COUNT(*) FROM item_groups WHERE group_key = ?)
WHERE group_key = ?;
```

4 个 worker 并发扫同组两个文件时会执行两次，但子查询是实时计数，SQLite 写串行，最终值都会收敛到正确结果。

### 只有一个分片时

照样写入，`part_count = 1`。UI 不渲染区块。等第 2 段出现，自动变成 2，不需要任何回改。

## 标题处理

`items.name` 的取值要单独定，否则列表里会出现两个同名卡片。

**决定**：`items.name = stem + " (" + part_index + ")"`，例如 `3070118 (1)`、`3070118 (2)`。

理由：

- 现在 `3070118_1` 解析出来的标题是 `3070118 1`（`cleanTitle` 把 `_` 换成空格），既脏又容易和年份混淆，要修；
- 名字里保留序号，列表页不需要前端改造就能区分两条记录，不会出现「上线后列表变两个一模一样的卡片」这种退化；
- 详情页区块仍然用兄弟列表 + 高亮，不依赖名字。

注意与 `[年份]` 括号的潜在混淆：年份通常是 4 位数且紧跟标题，序号是 1~2 位数并带分隔符，实际不会撞。

## API

### 新增

```
GET /emby/Items/{itemId}/Siblings
```

返回精简卡片列表，按 `part_index` 升序：

| 字段 | 说明 |
|---|---|
| `Id` `Name` | 卡片标题 |
| `PartIndex` `PartCount` | 用于按 `1/2` 渲染 |
| `RunTimeTicks` | 每段各自时长 |
| `ImageTags` | 沿用各自封面（分片通常共用同目录的 poster） |
| `UserData` | 各段独立进度 |

当前 item 也返回（带 `IsCurrent` 标记或由前端比对），这样前端不用拼接。

### 详情响应补充两个标量

`BaseItemDto` 增加 `PartIndex` / `PartCount`（`internal/dto/dto.go:48`）。

作用：详情页拿主接口就能画出 `1/2` 徽标，不必等兄弟接口返回，避免布局跳动。

### 为什么不直接塞进 `BaseItemDto` 的数组

99% 的影片没有分片。塞数组会让所有详情的响应体积和序列化开销都增加，而收益只对少数条目生效。独立接口可以异步加载，也能被前端以后复用。

## 前端展示

详情页新增区块：

```
本片共 2 部分
┌────────────────────────────────┐
│ [1] 3070118 (1)    48:32   ▶   │  ← 当前项高亮，不可点
│ [2] 3070118 (2)    48:10   ▶   │
└────────────────────────────────┘
```

四个交互细节：

1. 当前项高亮且不可点击。
2. 点兄弟项 **push 新的详情页**（可返回），不要替换当前页——用户会来回对比。
3. `part_count <= 1` 或没有兄弟时，整个区块不渲染，不留空框。
4. 列表页可选加 `1/2` 角标，避免用户误以为是重复扫描的 bug。

## 边界情况

| 情况 | 处理 |
|---|---|
| 缺号：只有 `_1`、`_3` | 仍成组。展示「第几项」用**组内排序位置**，不用原始序号，否则会出现 `1/3`、`3/3` |
| 完整版与分片共存：`3070118.mp4` + `_1` `_2` | 完整版无序号后缀 → 不参与分组，独立一条。这是正确行为 |
| 同目录多部片交错：`A_1` `B_1` `A_2` `B_2` | 按 `group_key` 天然分开 |
| 两段各有 NFO | 现有逻辑不变，元数据各自独立，不合并 |
| 删掉其中一个 part | purge 删 item + 删归属行，剩下的 `part_count` 刷新为 1，区块自动消失 |
| 同组排序 | 按 `part_index` 数字升序，**不能按字符串**（`_10` 会跑到 `_2` 前面） |
| 播放进度 | 按 `item_id` 独立，不聚合。点哪段播哪段 |
| `parsePartSuffix` 误判 | 写归属行前做一次结构校验：同组内 `video codec` 与 `width × height` 必须一致，不一致则放弃分组并记日志 |

最后一条是兜底：即使后缀规则误命中，结构校验也能拦住绝大多数错误关联。

## 决策记录

| 议题 | 决定 | 理由 |
|---|---|---|
| 单归属 vs 多对多 | 单归属（`item_id` 主键） | 一个文件只属于一部作品，成对表是浪费 |
| 是否建组主表 | 不建 | 组没有额外属性，`group_key` 字符串足够 |
| `group_key` 是否含目录 | 含（`library_id` + 相对目录 + stem） | 最保守，避免跨目录同名误关联 |
| 是否含 `library_id` | 含 | 两库同名文件不能串组 |
| 表名 | `item_groups` | 归属语义比 `item_relations` 准确；真要通用关系时再换 |
| 标题是否带序号 | 带，`stem (n)` | 列表页不改也能区分，避免上线即退化 |
| 关联失败是否阻断入库 | 不阻断，只记日志 | 关联是旁路能力，不能影响主流程 |

## 验收标准

1. 同一目录放 `3070118_1.mp4`、`3070118_2.mp4`，扫描后仍是两条记录，但两条都能在详情页看到「本片共 2 部分」。
2. 点第二部分能进入它的详情页并正常播放。
3. 删掉第二部分后再扫描，第一部分不再显示区块。
4. 只放一个 `3070118_1.mp4` 时，不显示区块，行为与现在完全一致。
5. 普通影片（无序号后缀）的详情页与列表没有任何变化。
6. 老库升级后不重新扫描也能生效（靠回填）。
7. 分片关联的表写入失败时，文件仍能正常入库并可播放。
